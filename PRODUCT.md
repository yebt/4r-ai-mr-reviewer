# Product

## Platform

web

## Users

Primary user: a developer, tech lead, or platform engineer who self-hosts 4R
against their own GitLab instance to review merge requests. The design center is
the **self-hosting community** — strangers who discover the repository, stand up
their own instance, and adopt it for real work. Today the app runs single-user;
multi-user/OAuth is on the roadmap, but the product is meant to be shared,
starred, and adopted widely, so a first-time self-hoster is a first-class
audience, not an afterthought.

## Product Purpose

4R is self-hosted AI code review for GitLab merge requests. The operator
configures GitLab accounts and an AI provider, tracks repositories, and runs a
review on any open MR. The engine loads the 4R rule sets, sends the diff to the
model, and returns located, structured findings with a deterministic score and
an approve / request-changes recommendation. The operator then chooses which
findings to publish back to the MR as inline discussions — optionally rewriting
them in their own voice first.

Success: the core loop **configure → review → publish** is fast, legible, and
trustworthy enough that a self-hoster keeps it in their real MR workflow, and a
newcomer can go from clone to first published review without friction.

## Positioning

4R reviews every change through four named lenses — **R1 Risk, R2 Readability,
R3 Reliability, R4 Resilience** — so the issues that matter most are caught
before production without slowing changes that are genuinely safe. Two things a
neighboring tool could not truthfully copy without becoming this product:

- The **4R framework as the organizing spine** of the whole experience — each
  lens runs as its own phased pass with live progress, and the recommendation +
  0–100 score are **computed deterministically from findings**, not asked of the
  model.
- **Self-hosted and private by construction**: the operator's code, diffs,
  tokens, and keys stay on their own infrastructure and provider account.

## Operating Context

- The user works inside a GitLab MR workflow: open MRs, diffs, inline
  discussions, approvals, pipelines, tags/releases. GitLab terminology (MR,
  discussion, project) is the native vocabulary of the product.
- Reviews are long-running and asynchronous: they run in phases with status
  polling and live per-phase progress; they can be retried (cloning the review
  and keeping the failed one for history), cancelled, archived, or deleted.
- The operator manages configuration surfaces alongside the review loop:
  GitLab accounts, AI providers (default + per-repo + per-review override),
  tracked repositories, style/voice profiles, Telegram notification targets,
  and release routines.
- Runs as a single self-hosted service (Go binary + SQLite) that the operator
  installs and administers themselves; the backend owns all state and is the
  single HTTP contract every client consumes.

## Capabilities and Constraints

Confirmed capabilities:

- **GitLab MR review** — list open MRs, fetch the diff (fast) or shallow-clone
  for deeper context (deep), run the phased 4R engine, publish selected findings
  as inline discussions; already-published findings are never re-posted.
- **Deterministic scoring** — recommendation and 0–100 score are computed from
  findings, not generated by the model.
- **Multiple AI providers** — OpenAI-compatible (Groq, OpenAI, Moonshot/Kimi,
  OpenRouter) and Anthropic (Claude), with a default provider, a per-repo
  provider/model, and a per-review override chosen at launch.
- **Humanize** — capture the operator's writing voice into style profiles and
  generate humanized versions of the summary and each finding, publishable per
  card.
- **Notifications** — Telegram targets (bot token + chat, optional topic
  thread), pings when a review finishes, test message, and chat/thread
  resolution from `getUpdates`.
- **Release routines** — resumable, ledger-based routines that verify, approve,
  compute a conventional-commit version, merge, tag, and notify.
- **Encrypted secret vault** — GitLab tokens, provider API keys, and bot tokens
  are AES-256-GCM encrypted at rest; the API never returns them.
- **Opt-in API auth** — password login + stateless signed httpOnly-cookie
  sessions; disabled by default (every route open).
- **Responsive web UI** — desktop sidebar and a mobile bottom-nav / "More"
  layout over the same feature set.

Durable constraints (binding — future work must preserve):

- **GitLab-first is product identity**, not a temporary limitation. GitHub
  support may be additive later, but the GitLab MR workflow and vocabulary are
  the center of the product.
- **Secrets never leave the operator's infrastructure.** Code, diffs, tokens,
  and keys stay self-controlled and encrypted at rest; the API never returns
  secrets. The private, self-hosted review pipeline is a security commitment.

Undecided / roadmap (do not present as shipped): GitHub support, webhook
auto-trigger polish, Telegram bot commands, multi-user auth/OAuth, loading-state
polish.

## Product Principles

- **The 4R framework is the spine.** Structure, language, and progress all
  express the four lenses; the review is the product.
- **Determinism where it counts.** Scores and recommendations are computed, not
  guessed — the operator can trust the number.
- **Private by construction.** Self-hosted, encrypted, secrets never returned;
  the operator stays in control of their code and credentials.
- **The operator is always in the loop.** The model proposes; the human selects
  what gets published and can rewrite it in their own voice first.
- **Adoptable by strangers.** As a serious OSS product, the path from clone to
  first published review must be legible to a newcomer, not just to its author.
